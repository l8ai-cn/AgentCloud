# Markdown 学习文件研发标准

用于把参考课程、论文、代码仓库、案例和实验资料研发成真正可教、可学、可练、可验收的 Markdown 学习文件。学习文件必须有课程设计方法论支撑：反向设计、课程对齐、任务中心教学、苏格拉底提问、通俗讲解、技术引用和必要配图。

## 1. 基本判断

Markdown 学习文件不是：

- 教师讲稿的提纲；
- 参考资料摘要；
- 概念词条；
- 任务说明；
- 实验 runbook；
- 评分标准；
- “学生理解什么”的空泛导学。

Markdown 学习文件是学生独立阅读后能完成一个学习动作的教材页面。它必须让学生知道：

- 我为什么要学；
- 我具体学什么；
- 我照着哪几步做；
- 如何照着示范做一遍；
- 做完以后交什么证据；
- 失败时先查哪里；
- 这个知识点如何连接后续章节。

## 2. 从参考资料到学习文件的研发流程

每写一个学习文件，先完成下面 8 张卡。

### 2.1 Source Card：参考资料卡

字段：

- 来源名称：仓库、课程、论文、文档或网页。
- 具体位置：文件路径、章节标题、函数名、Notebook 单元或 URL。
- 原始内容：该资料实际讲了什么，不要只写标题。
- 可用素材：概念、代码、图、命令、实验数据、失败案例、习题。
- 适合学生层级：入门、标准、提高、综合实践。
- 进入课程位置：第几章、第几个任务、第几个知识点。

硬要求：

- 不能只写“参考 hello-agents”。
- 必须具体到文件、代码块、函数、Notebook 或章节。

### 2.2 Knowledge Card：知识点卡

字段：

- 知识点名称：例如 Chat Message、Output Parser、ReAct Action Parser、Retriever MMR。
- 解决的问题：例如“模型输出不稳定，程序无法消费”。
- 关键概念：3-5 个即可。
- 输入：学习者或程序给什么。
- 处理：模型、程序、工具、状态、检索或人工分别做什么。
- 输出：可被检查的结果是什么。
- 常见失败：至少 2 个。
- 边界：什么时候不用它，什么时候需要更复杂方案。

### 2.3 Evidence Card：证据卡

字段：

- 学生提交物：代码、日志、Trace、JSON、报告、截图、配置或表格。
- 验收标准：怎样算通过。
- 失败证据：怎样证明做错了。
- 对应练习：随堂题、操作题、案例题或 quiz。

### 2.4 Pedagogy Card：教学方法卡

字段：

- 三问定位：学生为什么学、学什么、怎么做。
- 方法论对齐：学习目标、证据、活动和测验如何对应。
- 苏格拉底问题：至少 3 个递进问题，覆盖观察、解释、证据、边界或迁移。
- 通俗解释：术语首次出现时的人话解释、小例子、工程术语、失败现象。
- 学生差异：生成式 AI 基础较弱、较强的学生分别如何进入任务。

硬要求：

- 不能先堆英文术语，再补一句解释。
- 不能只有教师讲解，没有学生判断、举证或操作。

### 2.5 Technical Citation Card：技术引用卡

字段：

- 来源：仓库、官方文档、论文、课程、Notebook。
- 位置：URL、文件路径、章节标题、函数名、代码行、commit 或 Notebook 单元。
- 采用点：概念、代码、参数、流程、失败案例或实验数据。
- 学生核查方式：学生如何看到原文、运行代码或对照日志。

硬要求：

- 不能只写“参考某 GitHub 项目”。
- 引用 API 或版本变化快的框架时，必须先查官方文档或本地源码。

### 2.6 Visual Asset Card：配图卡

字段：

- 是否需要配图：是/否。
- 原因：流程复杂、组件关系、状态分支、方案对比、错误排查等。
- 图示类型：流程图、架构图、状态图、对比图、概念图、诊断路径图。
- 图片 prompt：生成图时必须写。
- 资产路径和 alt 文本：生成后必须写。

硬要求：

- 需要配图时，不能只写“此处插图”。
- 图必须服务学习目标，不能是装饰图。

### 2.7 Lesson Flow Card：教学流程卡

采用：

`问题入口 -> 激活旧知 -> 概念解释 -> 示例示范 -> 学生操作 -> 反馈检查 -> 迁移应用`

每一步必须写清楚学生动作，不能只有教师动作。

### 2.8 Reuse Card：课程衔接卡

字段：

- 上一章输入：本页依赖学生已经会什么。
- 本页产物：本页生成什么。
- 下一章复用：这个产物如何被后续章节使用。

## 3. Markdown 学习文件固定结构

除非用户明确要求其他格式，一份合格学习文件按以下结构写。

### 3.1 标题

格式：`# 任务名：知识点名`

标题要让学生知道本页要学什么，不要只写“教师讲授脚本”。

### 3.2 本页学完你要能做什么

写 3-5 条可观察目标，使用能检查的动词：

- 识别、区分、解释、画出、填写、改写、运行、解析、定位、验证、评估、重构。

避免单独使用：

- 理解、掌握、了解、熟悉、知道。

坏例子：

- 理解结构化 Prompt。

好例子：

- 能把一个自由问答 Prompt 改写成包含角色、任务、输入、输出 schema、约束和失败处理的结构化 Prompt。
- 能根据 3 条模型输出判断哪一条不能被程序解析，并说明失败原因。

### 3.3 为什么要学：一个真实失败场景

先给具体场景，再给失败样例，并回答三问。

要求：

- 场景必须和本章主产物有关；
- 失败样例必须具体；
- 让学生看到“不学这个会坏在哪里”。
- 明确写出“为什么学、学什么、怎么做”。

示例结构：

```markdown
学生输入一个学习主题，系统要生成学习卡片。
第一次实现只写了“请生成学习卡片”，模型返回了一段自然语言。
问题是：程序无法稳定抽取标题、关键词、难度和练习题。
因此我们需要把 Prompt、输出 schema 和输出检查放在一起设计。
```

### 3.4 苏格拉底引导问题

每页至少 3 个递进问题。问题要引导学生观察证据、解释原因、判断边界，不要只问“理解了吗”。

示例：

```markdown
1. 观察：这两次模型输出在哪些栏目上不一致？
2. 解释：如果程序要保存学习卡片，为什么这种不一致会造成问题？
3. 证据：你会用哪一条日志证明问题出在输出格式，而不是主题本身？
4. 边界：这个任务一定需要 Agent 吗？直接 LLM 调用够不够？
```

### 3.5 参考资料与技术引用怎么用在这里

列出 1-3 条主参考，必须具体。

格式：

| 来源 | 具体位置 | 本页采用什么 | 学生如何核查 |
| --- | --- | --- | --- |
| LLM Cookbook | `docs/C2/7. 检查结果 Check Outputs.md` | 输出检查和事实一致性校验思路 | 对照本页检查表 |
| Hello-Agents | `docs/chapter3/第三章 大语言模型基础.md` | Prompt、Token、模型幻觉边界 | 对照本页固定规则和输出限制 |

不要照搬参考资料。要说明“采用它的哪个教学素材”。

### 3.6 核心概念：先通俗后术语

每个概念用四句话讲清楚：

1. 用学生语言说它是什么；
2. 用本任务的小例子解释；
3. 给出工程术语和在代码/Prompt/报告中的位置；
4. 说明失败时会出现什么现象。

必要时用表格：

| 概念 | 在任务中的作用 | 可观察证据 | 常见失败 |
| --- | --- | --- | --- |

### 3.7 图示与配图

复杂流程、架构、状态、对比和错误排查必须有图示。需要图片时写：

- 图片教学目的；
- 图片 prompt；
- 图片路径；
- alt 文本；
- 图和正文的关系。

如果本页不需要图，写一句“不需要配图”的理由可以放入内部 `visual-asset-card`，不用展示给学生。

### 3.8 最小可运行示例

必须给出 Prompt、代码、配置或命令中的至少一种。

示例可以是伪代码，但必须能让学生照着实现。

要求：

- 有输入；
- 有处理；
- 有输出；
- 有检查方式。

### 3.9 教师示范：一步一步拆解

用“先做什么、看到什么、为什么这样做”解释。

每一步包含：

- 操作；
- 预期现象；
- 解释；
- 如果失败先查哪里。

### 3.10 学生练习：改一个地方并提交证据

练习必须小而具体。

合格练习：

- 修改 schema 增加 `difficulty` 字段，并提交 3 条模型输出和 parser 检查结果。
- 把工具参数从无参数改成带 `timezone`，提交 tool call JSON 和最终回答。
- 将检索 top_k 从 2 改成 5，比较命中文档和最终答案变化。

不合格练习：

- 完成实验。
- 思考如何改进。
- 阅读参考资料。

### 3.11 常见错误与排查

至少写 3 个错误。

格式：

| 现象 | 可能原因 | 排查方法 | 修复动作 |
| --- | --- | --- | --- |

### 3.12 提交物与验收

写清楚文件名和内容。

示例：

- `prompt_v1.md`：第一版 Prompt。
- `prompt_v2.md`：加入 schema 和约束后的 Prompt。
- `runs.jsonl`：至少 3 条运行记录。
- `check_report.md`：说明哪条输出失败、parser 报什么错、如何修复。

验收必须客观：

- 至少 3 条样例；
- JSON 能被解析；
- 日志包含输入参数、模型输出、检查结果；
- 失败样例有定位和修复。

### 3.13 自检题

每页至少 3 题：

- 1 题概念边界；
- 1 题操作判断；
- 1 题失败排查。

题目要能进入 `course-practice-builder` 的题库设计。

### 3.14 和下一节的关系

说明本页产物会如何进入下一节。

示例：

```markdown
本页生成的结构化输出和 parser 检查，会在下一节被封装进 LangChain OutputParser。第 2 章不会重新讲 schema，而是复用这里的学习卡片 JSON。
```

## 4. 备课必须包含的环节

一章课的备课至少包含 12 个环节。

| 环节 | 要回答的问题 | 产物 |
| --- | --- | --- |
| 学情分析 | 学生已有基础是什么，最大误区是什么？ | 学情假设与先修清单 |
| 课程定位 | 本章在整门课中解决哪一段能力链？ | 章节定位说明 |
| 方法论选择 | 本章如何使用反向设计、课程对齐和任务中心教学？ | methodology-note |
| 学习目标 | 学生学完能做什么？ | 可观察目标 |
| 验收证据 | 怎么证明学生会了？ | 提交物与 rubric |
| 参考消化 | 哪些资料真的被用到了？ | source-card |
| 技术引用 | 技术来源具体到哪里，学生如何核查？ | technical-citation-card |
| 知识点拆分 | 本章有哪些不可再拆的核心知识点？ | knowledge-card |
| 概念依赖 | 先学什么，后学什么？ | 知识点图谱 |
| 案例选择 | 用哪个真实案例承载知识点？ | 案例说明 |
| 引导问题 | 用哪些问题让学生先观察、解释、举证？ | socratic-question-list |
| 通俗讲解 | 术语如何先说人话、再给工程名？ | plain-language-note |
| 配图设计 | 哪些地方需要图示、prompt 和图片资产？ | visual-asset-card |
| 教学活动 | 课堂上学生做什么？ | 活动脚本 |
| 实操设计 | 学生如何运行、修改、观察？ | 实验需求单 |
| 练习测评 | 怎么随堂检查和章节测验？ | 练习与 quiz 需求 |
| 复盘衔接 | 失败如何总结，产物如何进入下一章？ | 章节交付单 |

## 5. 内容密度要求

一份学习文件如果只有抽象描述，判为不合格。

至少满足以下 6 条中的 5 条：

- 有真实参考资料路径；
- 有具体失败样例；
- 有 Prompt、代码、配置或命令；
- 有学生要修改的对象；
- 有可提交证据；
- 有错误排查表；
- 有自检题；
- 有前后章节衔接。

## 6. 禁止内容

禁止出现下面写法作为主要内容：

- “教师讲解本节知识点”；
- “学生理解相关概念”；
- “参考资料自行阅读”；
- “完成实验并截图”；
- “根据实际情况调整”；
- “略”；
- “本节主要介绍……”后面没有例子；
- “从输入、处理、输出、证据、风险五方面分析”但没有具体输入、处理、输出。

## 7. 质量审计清单

生成后逐项检查：

- [ ] 页面是否只围绕一个主知识点或紧密任务？
- [ ] 是否给出具体参考来源？
- [ ] 是否从失败场景进入？
- [ ] 是否有最小示例？
- [ ] 是否解释了模型、程序、工具、状态、检索或人工分别负责什么？
- [ ] 是否有学生动作？
- [ ] 是否有可提交证据？
- [ ] 是否有错误排查？
- [ ] 是否有自检题？
- [ ] 是否说明与上一节、下一节的关系？

缺任意 3 项，必须重写，不能交付。
